### Contract and current authority

`Module.EntryOperations()` exposes `ExecuteReviewOperation` and `ReadReviewOperation` on the existing Entry adapter. An owner must explicitly register `UseReviewOperationPolicy(profile, policy)` before serving; absent policy/pool or a joined caller transaction fails closed. Production KN consumer wiring remains #289 after actual dev integration. No implicit fallback to legacy Review.

Every execute/read/retry checks authenticated actor/tenant, MFA, valid server selected-context projection, registered profile actor, current owner policy and native Review authority/guard before receipt lookup. Owner policy must check current assignment, revocation, read-only, profile, department and target rights outside Forms transactions. Forms additionally binds the complete `SelectedSession.AuthorizationStamp`, sorted realm roles and resolved native scope/role/node plus the owner's authority version. The request cannot supply actor, tenant, role, authority or a digest. Exact target/template scope is rechecked under module/tenant RLS before looking up the anchor. Revocation during an already authorized in-flight request is not re-queried from external owners while holding Forms TX.

Actual production chain: `httpx.Authenticate` verifies token -> `accounts.Handler.Middleware` uses `ResolveContext` to verify context ownership, tenant, active assignment and expiry on each request -> registered `extension.SessionProjection` emits opaque immutable KN authority -> `extension.resolveFormActor` resolves Forms scope. `TestEntryReceipt288_ActualHTTPCurrentOwnerAuthority` invokes the supplier through that real chain using synthetic database fixtures and real signed test tokens; it verifies actor/tenant/MFA/assignment revocation and native delegated-authority denial. It does not install a production policy or claim an applied KN consumer rollout. Native supplier semantics use an independent explicit fixture owner.

Limitation #259: the selected context UUID is an application context/assignment identity. Current `Principal` has no unique verified OIDC `sid`/`jti` metadata. Separate OIDC logins that select the same context with identical authority cannot be distinguished. `AuthTime`, MFA/HasOTP and assignment/context IDs are not used or described as a unique login session. Owners cannot claim a stronger login-session guarantee until #259 supplies trusted metadata.

### Atomic result and recovery

The server normalizes operation UUIDv7, profile, period, unit, exact submission/version, decision and note identically for execute/read/digest. A domain-separated SHA-256 binds the full original request. The new journal stores the digest and decision, not another copy of note/form content. Callers must persist that full intent before dispatch and retain it for reconciliation.

The native period lock serializes review with submissions and terminal changes. Legacy and additive calls share the same four-eyes, current submission, already-reviewed, terminal, limit and workflow implementation. Native review, existing workflow decision/feed/outbox effects and receipt/audit ledger plus permanent anchor commit/rollback together. Applied result is selected by the exact inserted review UUID inside that transaction: actual ledger seq, actor, PostgreSQL event/recorded timestamps and workflow request identity. SQL proof binds that row's operation idempotency key and same-transaction recorded time. It is never head+1 or a current/successor projection.

A proven pre-effect native version/superseded/terminal/self-review/limit rejection can commit a rejected receipt with its exact code; infrastructure, INSERT, workflow or COMMIT errors return opaque unknown. A real COMMIT followed by lost ACK also returns unknown. Only a later authorized read of the exact durable receipt proves outcome. Unknown does not prove rollback or permit replacing the operation ID. Read never executes Review or inserts receipt data. Replay after a successor/ABA returns its own original result, without native mutation.

The permanent `(tenant, operation UUID)` anchor is INSERT-only, immutable and has no expiry. Receipt is append-only through `shared.apply_ledger`, with tenant RLS, and follows shared ledger partition retention; this package introduces no purge schedule. If receipt history is absent/purged/unavailable/inconsistent, the anchor blocks reexecution while lookup stays opaque unknown. A mismatched body/actor/current authority cannot replay prior applied proof. A different tenant cannot read another tenant's anchor or journal.
